## 状态机的组成

想必大家都不是第一天听说这个词了，之前前端框架也有自己的状态机，或者我们叫它仓库，像是 Vuex。

里面必备的几个属性，state，action，getter 等等，其实核心思想就是我现在有个对象，它有一些’状态‘，这不同的状态下又有不同的’表现‘，而我有几个动作，能改变它的状态。

再具体点，我有一只小鸡，只不过它现在的状态是只蛋，蛋的时候就不能吃虫子，也不能下蛋，我需要孵化这个动作，把它孵化成小鸡，就具备了吃虫子的能力。

到这里我们就可以引出状态机的四个核心概念：

* **State（状态）**：事物在某一时刻所处的稳定状况（如：草稿、待审批、已发布）。同一时刻只能有一个状态。
* **Event（事件/动作）**：触发状态改变的“因”（如：提交、拒绝、发布）。
* **Transition（流转/迁移）**：状态改变的“果”和过程。即：从状态 A 接收到事件 X，变成状态 B 的这个动作。
* **Action（动作/副作用）**：在流转过程中顺便执行的业务逻辑（如：发邮件通知、改数据库、扣库存）。

简单一句话就是，我有个存储内容的**状态变量**，还有几个能让它改变的**动作**。

## 状态机+显式图编排

LangGraph 就是在这个基础上开始设计，并融入了图编排的概念。

**State（状态包）**：是贯穿整个会话的唯一数据源，Reducer 算法，只做数据的合并和追加。

**Node（节点）**：能让状态改变的逻辑片段，可以写传统代码，也可以引入 LLM。

**Edge（边）**：连接节点的线，可分为普通边和条件边，普通边是以固定顺序连接节点的，而条件边会根据不同状态去跳转不同节点。

看到这个我直接联想到写业务之前会先画流程图，而这些节点、边就是流程图的具体代码表达。

闲话少说，直接动手实现吧。

## 业务实例

假设我们要实现的是一个天气查询的简单功能，因为咱们本章主要讨论状态机和图编排，所以不引入大模型能力了。

先画个图，预计的工程流程是这样的：

![补齐 decide 判断逻辑的 LangGraph 天气流程图](/notes/img/20261125-85177f66.png)流程非常清晰简单：

1. 首先进入 decide 节点，这个节点有业务逻辑，如果 tool_result 是有结果的，回复天气状态并标注 action 为 finish。如果 tool_result 没有结果，但是 question 中包含北京、天气，这些关键字，就将 action 改为 use_tool。条件都未命中就直接友好提示并标注 action 为 finish。
2. 紧接着进入条件边判断，如果 action 是 use_tool 则调用 weather 节点，开始天气查询，如果是 finish 就进入结束节点。
3. weather 节点查询结束后再通过普通边回到 decide 节点。

我们就通过这么一个流程图来实现天气查询的功能。

### LangGraph 实现

先用 LangGraph 实现一遍。

```python
from typing import Literal

from langgraph.graph import END, START, StateGraph
from typing_extensions import NotRequired, TypedDict


# State 声明共享字典里的字段。运行从 question 开始，
# NotRequired 表示其他字段可以等到对应节点执行时再写入。
class State(TypedDict):
    question: str
    action: NotRequired[Literal["use_tool", "finish"]]
    tool_result: NotRequired[str]
    answer: NotRequired[str]


# 2. 定义节点。每个节点只返回需要更新的字段。
def decide(state: State):
    print("  执行 decide")
    # 工具节点执行后会回到这里。此时可以用工具结果生成答案。
    if "tool_result" in state:
        return {"action": "finish", "answer": f"查询结果：{state['tool_result']}"}
    # 第一次进入时用关键词决定是否调用工具。返回值只包含要写入的字段。
    if "北京" in state["question"] and "天气" in state["question"]:
        return {"action": "use_tool"}
    # 普通问候可以直接生成答案，finish 会让条件边指向终点。
    return {"action": "finish", "answer": "你好！我可以演示查询北京天气。"}


def lookup_weather(state: State):
    print("  执行 weather")
    # 模拟工具调用。把结果写进共享状态，供下一次 decide 读取。
    return {"tool_result": "北京晴，22°C（模拟数据）"}


# LangGraph 先合并 decide 返回的字段，再调用 route 读取更新后的 action。
# route 返回分支标签，add_conditional_edges 的映射表将它转换成下一站。
def route(state: State) -> Literal["use_tool", "finish"]:
    return state["action"]


# 4. 注册节点和边，然后编译
# StateGraph 记录状态字段。add_node 建立节点名和函数的对应关系。
builder = StateGraph(State)
builder.add_node("decide", decide)
builder.add_node("weather", lookup_weather)

# START 是入口标记，实际执行的第一个节点是 decide。
builder.add_edge(START, "decide")
# decide 执行完，根据标签去 weather 或结束。
builder.add_conditional_edges(
    "decide",
    route,
    {"use_tool": "weather", "finish": END},
)
# 普通边：weather 执行完固定回到 decide。
builder.add_edge("weather", "decide")

# compile() 把图的定义编译成可运行的图。调度节点和合并状态由框架完成。
app = builder.compile()


# 5. 每次 invoke 都从给定的初始状态开始运行
if __name__ == "__main__":
    for question in ("北京天气怎么样？", "你好"):
        print(f"问题：{question}")
        # invoke() 运行到 END 后返回整份状态，这里只打印 answer。
        result = app.invoke({"question": question})
        print(f"答案：{result['answer']}")



```

langGraph 自带状态机，节点，边使用起来也非常便利，可以说非常适合程序员思路。

### 仿 LangGraph 状态机实现

我们再手动实现一套状态机试下：

```python
from typing import Literal, NotRequired, TypedDict


# State 声明共享字典里的字段。运行从 question 开始，
# NotRequired 表示其他字段可以等到对应节点执行时再写入。
class State(TypedDict):
    question: str
    action: NotRequired[Literal["use_tool", "finish"]]
    tool_result: NotRequired[str]
    answer: NotRequired[str]


def decide(state: State):
    # 工具节点执行后会回到这里。此时可以用工具结果生成答案。
    if "tool_result" in state:
        return {"action": "finish", "answer": f"查询结果：{state['tool_result']}"}
    # 第一次进入时用关键词决定是否调用工具。返回值只包含要写入的字段。
    if "北京" in state["question"] and "天气" in state["question"]:
        return {"action": "use_tool"}
    # 普通问候可以直接生成答案，finish 会让条件边指向终点。
    return {"action": "finish", "answer": "你好！我可以演示查询北京天气。"}


def lookup_weather(state: State):
    # 模拟工具调用。把结果写进共享状态，供下一次 decide 读取。
    return {"tool_result": "北京晴，22°C（模拟数据）"}


def route(state: State):
    # 返回分支标签，由 branches 把它转换成下一站。
    return state["action"]


# END 是停止标记。nodes 用节点名找到对应的 Python 函数。
END = "__end__"
nodes = {"decide": decide, "weather": lookup_weather}
# 普通边：weather 执行完固定回到 decide。
edges = {"weather": "decide"}
# 条件边：用 route 返回的标签查出下一站。
branches = {"use_tool": "weather", "finish": END}


def run(initial_state: State) -> State:
    # 复制输入字典，避免本次运行直接修改调用者传入的字典。
    state = initial_state.copy()
    current = "decide"  # 指定第一个执行的节点。

    # 图里有回路，限制最多执行 10 个节点，避免分支写错时一直循环。
    for _ in range(10):
        print(f"执行 {current}")
        # 先执行当前节点，再把返回的字段合并进状态。
        update = nodes[current](state)
        state.update(update)

        # 合并之后再选边，route 才能读到 decide 刚写入的 action。
        if current == "decide":
            current = branches[route(state)]
        else:
            current = edges[current]

        # 到达结束标记就返回整份状态。
        if current == END:
            return state

    raise RuntimeError("超过最大节点执行次数")


# 两次独立运行，分别观察走工具和直接结束的路径。
if __name__ == "__main__":
    print(run({"question": "北京天气怎么样？"})["answer"])
    print(run({"question": "你好"})["answer"])

```

关键节点逻辑都一样，状态机也都一样用类来实现。

需要注意的就是手搓版是需要实现节点、普通边、条件边的集合的。

```python
# 节点
nodes = {"decide": decide, "weather": lookup_weather}
# 普通边：weather 执行完固定回到 decide。
edges = {"weather": "decide"}
# 条件边：用 route 返回的标签查出下一站。
branches = {"use_tool": "weather", "finish": END}

```

并且在运行方法中要自己做好状态的更新合并，以及循环的轮数限制等边界情况。

总结来说，langGraph 的状态机和图编排都不难写，主要是节点、边的集合、状态更新、不同边的逻辑分支。

但是 langGraph 的设计的确是能充分发挥大模型思考优势，又能给它画好行为轨迹，竖好边界的典型 harness 工具，如果业务上需要顺序性，流程性的工作，这种框架是再合适不过了。
