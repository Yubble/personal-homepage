# 多 Agent 也不是滴水不漏

近日刷自媒体的技术文章，被多 Agent 架构这个概念吸引，本着我们老研发人的好奇心驱使，便让开发工具快速搭建了一个多 Agent 协同的智能体。整体架构可以大致理解成这样：

![image.png](/notes/img/20261119-e77da3a6.png)

这种架构并不是常说的父子 Agent 结构，**Supervisor**并不是一个 LLM，他做的事情就是流程调度，以及做意图路由识别，而后面的几个子 Agent 各自并行隔离。

您可能会问为什么要这么设计，最核心的一点：省钱！我们在路由调度节点设计了三层判断，第一层关键词，第二层语义向量，这两层都是可以提前预设的，0 成本，对于一个咨询型 Agent 来说，70%以上都是这些问题，没必要在这些鸡毛蒜皮上浪费我们的 token，最后一层用 LLM 兜底，各种关键词都没有命中的情况下，大模型来判断。

紧接着按意图划分进入子 Agent，进行下一步行动及回复。

## 问题一、子 Agent 工作流串行，无法识别出多个意图

看到上面这个架构，各位读者觉得子 Agent 各有各的分工，各自有各自的深耕对吧。但是问题来了。

如果我问一个问题同时带有两个意图，比如”我的车抛锚了，你们有救援服务吗？另外你们有米其林的轮胎可以换吗？“

这句话其实带着两个意图，一个是‘救援询问’，一个是‘售卖报价询问’，而现有的架构会导致流程串行到子 Agent，也就带着这两个问题同时访问了优先级较高的救援 Agent，输出结果就是救援问题回答的非常彻底，售卖询价问题只字不提。

针对这个缺陷，在 Supervisor 上既增加了多意图识别的能力。

![image.png](/notes/img/20261119-e9cb37fc.png)

需要在路由识别阶段进行意图数量确认，后续可同时启动不同子 Agent 进入工作，便可同时处理一句话中多个意图。

## 问题二、脱离上下文的对话

细心的读者可能已经观察到，我们如果拆分不同 Agent 的话，那么如果输入一个脱离上下文的问题，则很难判断这句话应该划分给哪个子 Agent。例如：

”我的车抛锚了，你们有救援服务吗？“

”你们那处理这种问题什么报价“

很明显这种问题指代的是救援服务，但是子 Agent 本身就是单一职责，它是个不携带任何上下文的黑盒工程师，只负责从上游接到任务，然后执行。

所以我们在意图路由阶段又增加了一层上下文，来判断代词的指向。![image.png](/notes/img/20261119-b02bdfd2.png)

根据现在的架构图来看，Supervisor 这个意图路由大脑又厚了一点，由它来参考上下文，判断问题代词指向哪里

但是可能还会碰到多意图咨询，那么这时候的代词又应该指向哪里呢？

我的答案是，让 Agent 做一次模糊追问，不猜了，毕竟有人这么问他自己可能都没想清楚。

至此多 Agent 的坑也都填平了。

## 为什么会有这些缺陷

严格来说我们这种架构还不算是标准的多 Agent 架构，像 Claude Code 一样多 Agent 是需要有一个统一的父 Agent 来做调度的，什么模糊问题，多意图，上下文全都要在父 Agent 那里过一遍，让他来思考判断。

但是话又说回来了，我们这个场景搞父子 Agent 实在是高射炮打蚊子。一个边界分明的意图路由没必要接入成本高昂的 LLM 来做分发，同时父 Agent 调度子 Agent 全靠它的判断，我们无从插手和抉择，流程更是不可逆的，如果是复杂多变的场景（像是代码编程）父 Agent 确实能发挥不可替代的作用，但这种规则清晰，业务隔离明确的场景，并行子 Agent 已经绰绰有余了。
