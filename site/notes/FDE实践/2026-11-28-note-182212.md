# 六大失败模式

之前讨论了 FDE 入场后要做什么，如何正常推进以及高质量交付，今天这篇文章来讨论 FDE 容易走入哪些陷阱泥潭，以及如何规避这些风险。

FDE 通常是由资深的工程师来担任，且需要长期入驻到客户公司，独自面对多方压力，毕竟 FDE 也是人，在高压的逼迫下容易落入下面的陷阱。

### 咨询陷阱

平台的代码中，客户专属型代码增长飞快，慢慢的团队的重心就从打磨产品转成了维护客户的咨询外包公司。

解决这个问题还是要遵守平台沉淀的规则，拒绝无法沉淀的功能交付。

### 客户雪花化

每个客户定制的功能都不一样，后期花费大量的人力来定向维护客户，成本爆炸。

所以每个客户交付之后都应留下一套可复用的模版，而团队接到任务的第一反应应该是“套用哪个已有模板”，而不是为了留下这个客户给它做单独实现。

### 英雄工程师

过度依赖一个资深工程师，经验和技术只在他一个人身上，其他人无法插手。如果这个人离职没有任何可沉淀的知识能留下。

每个客户配两名工程师，且需要把关键工作和认知写成文档。

### Demo 债务螺旋

有些不太成熟的团队为了在前期博得客户好感，会在 Demo 演示时过度承诺产品的效果，但是在研发、联调的过程中会有很多不可预料的灾难，脏数据、权限问题、成本规模等等。

而解决这种问题的最好办法就是，一开始就不要过度承诺。并且在验证期间，多使用并暴露脏数据，也不压缩硬化阶段的时间。

### 赞助人崩塌

高管离职实际上是一个能让项目震动的事情，无论是多么有潜力的项目也未必扛得住。

之前的笔记中讨论过这种情况，应尽早着力发展多赞助人，并且尽快建立自下而上的适用场景，让项目早日生根立足。

### 倦怠死亡螺旋

前面说过，FDE 会长期承担高压工作，如果缺少团队轮换以及良好的职业发展通道，FDE 的倦怠就会逐渐积累，最早的预兆就是资深工程师率先离开，留下的人越来越懈怠。

针对这种情况有以下四种对应方式：

1. **刻意轮换**。不要让 FDE 长期固定在一个客户上，没有知识积累曲线了就可以进行轮换。
2. **强制修整**。高强度交付后主动安排一些休息时间。
3. **建立同伴互助机制**。关键的客户不能只由一人负责，让现场压力和关键知识都有人分担。
4. **建立清晰的职业发展通道**。什么时候可以晋升，不走管理岗也能有其他发展方向。

以上就是会影响 FDE 团队以及项目交付质量的六大因素。
