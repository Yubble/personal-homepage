# AI 项目怎么验收和上线

前面我们讲了项目怎么做，接下来讨论一下项目怎么验收上线。

### 先做评估集

AI 项目有个特点，它的好不是有标准的好，不像从数据库中查数，每次都是幂等的答案。

“这周最优惠的拼单方式是什么？”，“店里适合越野的轮胎有哪些”，这些开放性问题很难有固定的标答。传统 PRD 的要求“回答要准确”就很难推行下去。

所以我们需要先把好的标准定义出来，这套方法有个名词，叫“**评估驱动开发**”。而测试用例也变成了一个新词，**评估集**，而它和用例最大的区别是，它需要先写。因此顺序就变成了：

一、和客户一起把好的标准写下来，什么能说，什么不能说。

二、把这些标准变成一条条用例，构建评估集。

三、搭好 Harness（限制器）

四、编写 Prompt，搭 Agent

随着 Agent 的搭建，我们可能会遇到要调整评估集的情况，但是有个原则要牢记，**用例可以补充，但是修改一定慎重**，毕竟不应该是出了问题就解决提问题的人。

评估集的重要性是显而易见的，不管是换模型，还是改 Prompt，它都能告诉你功能有没有变，有没有改错，哪怕后面大刀阔斧地重构，评估集都永不过时。

### 评估集分类

* **黄金集**：核心场景标答。这里答案必须唯一，可以逐字比对。
* **异常场景集**：收录怪情况。没人写进文档的，千奇百怪的奇葩场景。比较难收集，可以让两个 Agent 同时跑，跑出的差异就是异常。
* **安全对抗集**：故意问超出安全边界的问题，测试它能不能守住安全边界。

三类评估集的上线标准是不一样的，黄金集需要接近满分，异常场景集需要逐步提升，但是不能低于上次得分（棘轮效应），安全对抗集只要出了问题，立刻停止开发，进行排查。

而 Agent 在上线之后，客户往往会问出之前从没想过的问题，这才是最有价值的，要立刻补充评估集。

### **评估集谁说了算**

尺子往往要在项目启动前做好，那究竟是谁说了算？

曹犟先生的建议是：

系统质量标准、评估集维护、回归纪律，这些属于评估面，由 FDE 负责。因为客户不需要介入具体的工程。

业务口径是否正确、结果是否有价值、最终验收是否通过，这些属于客户面，由客户负责。因为 FDE 不应该替客户拍板。

评估的目的不是通过验收，它是贯穿项目的重要部分，除了评估之外，还要回到现场看客户到底怎么用。

### 罗列检查清单

评估过了，就需要我们打上线前的最后一战，怎么通过 CIO，安全负责人的审核。答案就在一张上线检查清单上。

一、**评估过线**。黄金集接近满分、异常场景集达标、安全对抗集全部通过。

二、**真实规模下的性能与成本**。线上的规模可能是测试阶段的千倍万倍，需要在上线前按照线上规模测试一遍，Token 的成本，延迟效果能不能接受。

三、**安全与权限**。脱敏、白名单最小权限是不是都完成。

四、**全链路留痕与决策可追溯**。

五、**应急与回滚预案**。降级兜底方案是什么，Agent 死循环怎么一键停止，有没有数据回滚演练。

六、**运营与交接流程**。线上运营需要注意什么，怎么接收告警，文档是否留存。

### 落实负责人

只要是工作就会有疏漏，把各类风险落实到对应负责人上能分工明确地推进。

|            | 问题表象                             | 负责人                       |
| ---------- | ------------------------------------ | ---------------------------- |
| 模型风险   | 模型答错、失准                       | 首席风险官或者数据科学负责人 |
| 数据风险   | 输入泄露、数据漂移、被投毒           | 安全负责人                   |
| 工作流风险 | 被 AI 重新设计过的流程产出了错误结果 | 运营负责人                   |
| 供应商风险 | 模型厂商断供、涨价                   | 采购                         |
| 治理风险   | 全链路留痕不完整、无法回答合规问题   | 合规团队                     |

有了这个对照表，我们能清晰知道线上出了问题，应该怎么定性，由谁来负责。

### 全链路留痕及人工检查

清单和分工都有了，但是真正能把这些串起来的是**留痕**。

一个由 Agent 错误理解导致的线上事故，其源头究竟在哪儿，是知识库出了问题，还是历史数据过期，又或者模型判断失误。如果有全链路留痕就有追溯，且全链路起码要留一年，中间每隔一个月可以拿出来晒一晒，复个盘。

不光是 FDE 需要，站在客户的角度，他们也会关注，基本上分为这四类：

* 决策依据：为什么这么判断。
* 数据来源：数据库里的，还是模型判断的。
* 操作记录：它都做了什么。
* 反向回滚：打错了能不能撤销。

以上解决了出事怎么办的问题，而**人工检查**是让我们在出事前能有机会甄别。

不是所有的事都需要人批，那这个 Agent 离不开人了，但是又不能事事都放行。可参考下列原则：**低风险动作，比如查询、汇总，由 Agent 自主完成；高风险动作，则设置强制的人工确认。**

至于哪些是低风险、哪些是高风险就由业务具体判断了。（个人认为涉及到花钱的，一定是高风险）

其次，人工检查是个由严到松的过程，也是给 Agent 留充足的学习时间，我们需要根据 Agent 建议的采纳率，以及之后的兑现率来判断是否可以让 Agent 在决策时有更大的权限。

讲到这里，上线前的关键动作也应该都讨论完了，希望工作的沉淀能把这些知识融会贯通，让我们学有所得，有所收获。
