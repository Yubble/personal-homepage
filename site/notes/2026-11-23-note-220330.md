# RAG 的索引和检索

说到 RAG 技术，应该是我们用 AI 技术赋能现有传统业务最有价值的部分，毕竟 AI 来翻文档，总结归纳可比人要强多了。

而它的技术点主要由两部分模块组成，索引和检索，那么他们都是怎么工作和实现的，我们今天来学习探讨下。

## 离线索引

这一步的链路是这样的。

***文档加载 → 清洗 → 分块 Chunk → Embedding → 入库***

#### 文档加载

简单来说企业的现有数据，资料，文档等都在以五花八门的形式分散着，有的是.doc，有的是.pdf，有的是图片，还有些是 SQL 里的数据。

所以要将文档统一收集上来，并且转成计算机能看懂的文本格式，这里可以用到的技术栈有很多，比方说 pdfplumber，unstructured 等，并且通常要接入 OCR 技术。

如果文档量不大且差异性不多我比较推荐 markitdown，直接生成 md 文档，对计算机读取天然友好，适合 POC 演示。

#### 文本清洗

这个环节就是去掉脏数据和脏文本，去掉空行，剔除页眉页脚等无用内容。

虽然市面上的清洗工具很多，但是这里建议尽量做轻，本着”**宁少删，不误删**“的原则。

#### 切片

现在到了索引最难的环节，因为 AI 在索引的时候是找 token，不是找长文本，所以需要给收集上来的长文本进行切片，也叫切 chunk。

这时候就需要接入现成的工具，各个框架都有自己的切片工具，至于切多细，从哪个维度来切是可以编辑设定的（按行切，按字数，或者按特殊字符）。

这时要根据具体业务形态来调整切片的颗粒度，比如法律条款就禁止跨条款切割，产品规格书则不存在叙述性内容，可以精细切割，而如果是长表格的话就需要将表格按行来进行切分。

#### Embedding 向量化

这个阶段我们已经把长文本切成 chunk 了，但是这个时候也还是文字，计算机是看不懂的，就需要把文字转成向量，也就是一堆数字。

而 Embedding 也算是个小模型，它是具备一部分思考能力的，这个阶段就可以让它来将向量的相似度进行计算，比方说’早安‘和’早上好‘就是语义相似的 token，那么它们的向量距离就会比较近。

这个技术叫做稠密向量。

我们也可以同时做稀疏向量，它的作用是精准匹配关键词，比如说现在需要召回订单编号 230 的退款信息，稠密向量是没办法通过相似度找到这个编号的，那么这时候就需要精准查询编号 230 的信息，再结合稠密向量观察到退款信息这个向量词，而联想到退款步骤进行精准的查询操作。

简单来讲稠密向量（BGE-M3）是理解语义，稀疏向量（BM25）是精准查询。

#### 向量入库

把向量、chunk、元数据存入向量数据库。

这类数据库有很多，Milvus 是市面上用的比较频繁的一个。

值得注意的是元数据也是需要入库存储的，后面溯源，引用都需要用到。

## 在线检索

到了检索环节，链路就变成了：

***用户 Query → Query 预处理→ 多路召回（稠密 + 稀疏） → Rerank 重排 → 上下文组装 → LLM 生成 → 后处理***

#### Query 预处理

将用户输入的问题用大模型进行清洗以及增强。

**清洗：**用户发来的问题可能多出空格，多几个标点，或者多打了很多相似的文字，这些都是大模型不需要也不想分析的事情。

**增强：**用户发的问题可能偏于口语化，或者存在上下文缺失，又或者存在多个意图，那么这时候增强就起到改正，补充的作用了。

此时会消耗一点点 LLM 算力，将用户输入的模糊的问题转变为大模型看得懂的文字。

#### 多路召回

拿处理好的 query 信息，同时执行两路检索，就是我们之前提到过的稠密向量和稀疏向量。

**稠密召回**是将 query 转向量，去向量库找最接近语义的 chunk，并返回相似度靠前的几项。

而**稀疏召回**是将 query 做关键词切分，再去稀疏向量库做匹配，同样返回 top 几项。

最终由 RRF 算法将两路融合，并重新排序后合成列表返回。

（注：RRF 虽然是有一个参数的算法，但是基本不需要调参）

#### Rerank 重排

只将稠密和稀疏双路召回还不够，里面依然混杂着很多不相干的 chunk，如果此时将 chunk 返回则容易造成召回噪声，让大模型理解出现偏移。

因此我们需要再将用户问题对照每一条召回的 chunk 逐个对比打分，根据‘这一段能不能回答用户问题’来挑选最优答案。

这里我们和向量召回做一下区分，向量召回是把语义相同的或者文字相近的 chunk 找出来，但是它不确定找回来的 chunk 能不能回答用户问题，而 Rerank 作为一个小模型，也是有思考判断能力的，这里就由它来判断哪个 chunk 是能回答问题的。

#### 上下文组装

这个时候精准可用的 chunk 就已经被挑选出来了，把它们和 prompt 的约束以及用户的问题一同发给大模型，让他来总结回答就可以了。

格式可以想象成这样：

> 【系统约束】 你只能使用下面【参考资料】里面的内容回答用户问题，资料没有的信息，直接回复暂无相关资料，禁止编造。
>
> 【参考资料】
>
> 1. xxx
> 2. xxx
>
> 【用户问题】
>
> xxx

#### LLM 生成

大模型此时终于出场了，根据前面环节给到的资料 chunk，约束，问题，总结梳理成可回答的一句通常的话语，到此来看其实大模型做的事情很少，真正操作繁重的地方都在前面流程。

故而如果出现了一些意想不到的意外，可以根据现象，再全流程排查。例如：

问题一、幻觉，编造不存在的数字，条款等。

措施：此时就可以查看是否给大模型做了只根据资料答疑的 prompt 约束，并且有没有进行答案自校验，并要去输出引用编号等

问题二、想要 JSON 结构化输出，格式经常乱掉

措施：使用模型原生 Structured Output / JSON Mode + Pydantic 校验；

其实到了这个阶段的错误排查，第一件要做的事就是看链路监控，到底是哪一个环节出现了偏差。

#### 后处理 & 校验

拿到 LLM 输出的答案之后，再做一轮检查，比如答案中的数字、文字等能不能在 chunk 中溯源到，去掉多余废话，校验不上的内容标记风险。

简单的说就是让 LLM 再检查一遍，对自己说的话负责。

至此一个 RAG 的索引和检索全流程就梳理清楚了，梳理之前我对这部分知识也是一知半解，梳理之后整体对它的轮廓已经有了大概印象，还是很有收获的。
