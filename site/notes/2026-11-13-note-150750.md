# FDE 关键人、关键事

前面我们讨论了怎么入场，怎么找关键指标，自信满满的你先别忙着开工，因为还有一个关键的变量需要我们去梳理，那就是‘人’。

在中国关系网是个很微妙的东西，我和你关系好，信任你，可以举着钱来助你创业。我如果不认识你，你技术再强也很难从我这拿到资源。

况且 FDE 是入驻到别人公司的，本身就有种分蛋糕的错觉，这时找到赞助人和怀疑者，守住信任边界就非同小可了。

## 干系人地图

进场后除了快速熟悉业务，把相关的干系人找出来也很重要，他们是能影响项目命运的人。

| 角色（真名）         | 能拍板什么         | 能否决什么 | 需要知道什么       | 在意什么             |
| -------------------- | ------------------ | ---------- | ------------------ | -------------------- |
| 赞助人（王总）       | 预算与优先级       | 整个项目   | 业务结果与风险     | 营业指标             |
| 把关人（IT 负责人） | 技术方案与数据权限 | 上线流程   | 安全与合规细节     | 系统安全、团队话语权 |
| 使用者（小李）       | 用不用、怎么用     | 效果反馈   | 自己的操作怎么改变 | 工作会不会更顺手     |
| 怀疑者（老周）       | 技术评审意见       | 技术口碑   | 真实测试结果       | 别被供应商坑         |

而画完地图后还要圈出三类关键人。

对于手握权力，**能杀死项目的人**，要低频高质量的同步，让他脑子里是对项目有清晰进展以及风险的把控。

对**能拖延项目的人**，要提前把资料备齐送到，并充分尊重其专业性。

对**能放大项目的人**，重点服务，让其成为最先使用出效果的人，并主动宣传。毕竟外来者自夸一百句，不如自己人的一句肯定。

而赞助人和怀疑者则是我们需要重点发展的人。

**赞助人**是我们推动项目的强力帮手，可以的话尽量发展多个赞助人，并且建立自下而上的使用习惯。这往往需要我们有充足的汇报能力。

**怀疑者**一定存在，他会千方百计地阻碍我们发展以及落地，而攻破他则需要给他一个真实的角色，比如让他来做第一个内测使用者，如果顺利的话可以把他拉到拥护者的阵营来。

## 一个闪亮的 Demo

找到关键人之后，一个漂亮的 Demo 是我们要和他打交道的第一个本钱。

比起上百页密密麻麻的方案，一个 Demo 足够说明我们的工作能力与业务理解，同时它还有一个最重要的作用——**让客户说不对**

原型是对内的，Demo 是对客户的，让客户在看 Demo 演示的时候指出其中的问题比给他讲几百页的 PPT 方案要来得划算得多，客户带着好奇集中精力看演示也是拉近你们彼此信任的绝佳机会。

让客户说不对不是指你的 Demo 做得有 bug，是业务流程上有需要改正的地方，不要拿着主流程都走不通的半成品让客户检阅，那是对客户的不尊重。

所以选一个窄但是能通的业务流程做 Demo 是个至关重要的事，可以参考下面两个标准。

1. MVP（最小可行产品，证明哪个值得做）
2. MVA（最小可行架构，证明它是能做成的）

选好 Demo 方向后，保持每周演示一次，并且收集模糊反馈，它们都是可以变成工单的。具体为：

1. 客户具体的反馈（需要改进的地方）
2. 客户的迟疑环节（哪些功能他不感兴趣，哪些他在反复追问）
3. 双方的承诺（客户答应你的权限，你许诺完成的功能）

而如果一个 Demo 到成单，又是一个繁琐的过程，不是所有 Demo 上的功能都可以成为可交付的产品，需要经历下面的考验：

1. 主动暴露长尾和脏数据（不要只用干净的数据样本，也要掺杂非标的烂数据，让客户看到 bad case 下的兜底并管理预期）
2. 上生产前的加固（边界、监控、压测、回滚）
3. 降低客户对 Demo 演示后的期望（如果 Demo 阶段许诺预期过高，成品撑不住，会成为后续反复拉扯的诱因）

基于以上的因素，我们对 Demo 有一个正确的认识，**它是让我们继续走下去的资格，不是一个赢得合同的最终密钥**。

就此就要再提一次汇报的重要性，这也是让我们在工作推进中步步为营的强力抓手。
